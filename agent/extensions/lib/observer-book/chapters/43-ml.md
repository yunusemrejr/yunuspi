# Machine learning engineering

Most machine learning failures are not about model architecture. They are about data, evaluation and deployment: leakage that inflates results, metrics that do not match the product goal, and models that degrade silently when the world changes.

## Start with a baseline {#baseline}
<!-- terms: baseline simple heuristic majority class linear model logistic regression benchmark compare -->

**Principle.** Before training anything complex, measure a trivial baseline (majority class, simple rules, linear model) and require the complex model to beat it meaningfully.

**Why.** Baselines reveal how hard the problem really is and expose broken pipelines: a deep model that barely beats predicting the most common class is not learning much. Simple models are cheaper, faster, more interpretable and easier to maintain. Many production problems are solved well enough by heuristics plus a simple model.

**Signals.** Complex models reported without baselines; improvements claimed over weak or outdated baselines.

**Ask.** What does the simplest reasonable approach score, and how much better is the proposed model?

**Traps.** Baselines deliberately weakened to make models look good.

## Hunt for leakage {#leakage}
<!-- terms: leakage leak train test contamination future information target leakage split temporal duplicate -->

**Principle.** Ensure no information from the test set or the future leaks into training—split by time or entity, fit preprocessing on training data only, and deduplicate across splits.

**Why.** Leakage produces spectacular offline metrics that collapse in production. Common forms: random splits on time series (training on the future), normalization fitted on all data, duplicates or near-duplicates across splits, features derived from the target (a "cancelled_at" field predicting churn), and the same user in train and test. Suspiciously good results are usually leakage.

**Signals.** Random splits on temporal data; preprocessing before splitting; near-perfect validation scores.

**Ask.** Could any feature or preprocessing step carry information unavailable at prediction time?

**Traps.** Leakage through hyperparameter tuning on the test set.

## Evaluate the way the model will be used {#evaluation}
<!-- terms: evaluation metric offline online slice segment calibration threshold precision recall business metric -->

**Principle.** Choose metrics that reflect the product decision, evaluate on data resembling production, and examine performance across important slices.

**Why.** Accuracy is misleading for imbalanced problems; AUC does not tell you performance at the operating threshold; aggregate metrics hide failures on minority segments. The right metric follows the cost of errors (false positives versus false negatives), and slices (by region, device, customer type) reveal where the model fails. Calibration matters when scores are used as probabilities.

**Signals.** Accuracy on imbalanced data; no per-segment evaluation; threshold chosen arbitrarily.

**Ask.** Which errors are costly in this product, and does the evaluation metric and slice analysis reflect them?

**Traps.** Optimizing an offline metric that does not move the online goal.

## Data quality beats model tweaks {#data-quality}
<!-- terms: data quality labels noisy labels annotation cleaning more data distribution class imbalance augmentation -->

**Principle.** Invest in label quality, coverage and data cleaning before architecture or hyperparameter tuning.

**Why.** Models learn what the data teaches, including its errors. Noisy labels cap achievable performance; missing coverage of important cases guarantees failures there. Reviewing misclassified examples usually reveals labeling problems or missing data faster than tuning reveals anything. Data-centric iteration—fixing labels, adding targeted examples—often yields larger gains.

**Signals.** Extensive hyperparameter searches with no error analysis; label quality never audited.

**Ask.** What do the model's errors look like, and are they caused by data or by modeling?

**Traps.** Collecting more of the same data instead of the missing cases.

## Make experiments reproducible and tracked {#tracking}
<!-- terms: reproducible seed experiment tracking mlflow wandb version data version config checkpoint -->

**Principle.** Record code version, data version, configuration, seeds, metrics and artifacts for every experiment.

**Why.** Without tracking, the best model cannot be reproduced, comparisons are unreliable and regressions cannot be explained. Seeds reduce variance but multiple seeds reveal it. Data versioning matters as much as code versioning because datasets change, and an unrecorded filter or sample can explain an entire metric difference.

**Signals.** Results reported from runs that cannot be traced to exact code and data; single-seed comparisons of close models.

**Ask.** Could this model be retrained exactly from recorded code, data and configuration?

**Traps.** Tracking so heavy it discourages experimentation.

## Serving has its own constraints {#serving}
<!-- terms: serving inference latency throughput batch quantization onnx gpu memory cost deploy model size -->

**Principle.** Design for inference constraints—latency, memory, throughput and cost—early, and verify that the deployed model reproduces offline predictions.

**Why.** A model that wins offline may be too slow or large to serve. Quantization, distillation, batching and caching trade small accuracy for large efficiency gains. Training-serving skew—different preprocessing in production—silently degrades predictions; comparing online and offline outputs on the same inputs catches it.

**Signals.** Model choice ignoring latency or cost; preprocessing reimplemented separately for serving; no parity test.

**Ask.** What are the latency and cost budgets for inference, and does the served model match offline predictions?

**Traps.** Optimizing inference before the model is validated.

## Monitor for drift and degradation {#monitoring}
<!-- terms: monitoring drift data drift concept drift distribution shift retrain feedback loop performance decay -->

**Principle.** Monitor input distributions, prediction distributions and delayed ground-truth performance, and define when to retrain.

**Why.** The world changes: user behavior shifts, new products appear, upstream data changes. Models degrade silently because they still produce confident outputs. Monitoring input drift gives early warning; tracking performance on labeled feedback confirms degradation. Feedback loops (the model influencing its own future training data) need special care.

**Signals.** Models deployed without monitoring; no retraining plan; predictions influencing future labels.

**Ask.** How would we know this model had become wrong in production?

**Traps.** Retraining on schedule without checking whether the new model is better.
