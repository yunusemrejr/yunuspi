# Harness maintenance boundary

The guard captures launch-directory authority when its module first loads. Human launches inside the active harness root (the root itself or a descendant) can maintain it and receive a maintenance reminder. Launching from home, `/`, a parent directory, or a similarly named sibling does not grant authority. Subagents have no independent maintenance authority. Changing a tool's cwd does not change the captured authority. A resumed conversation uses the current process launch authority, not the old transcript.

Direct write/edit, bulk apply and snapshot restore check the active harness path. Resolution follows symlinks before interpreting `..`, including dangling links and nonexistent descendants. Unlinking an outside symlink removes that entry and does not count as writing its referent; writes through it remain protected. Guarded executable tools use a Linux read-only mount boundary, inherited by their descendants. Unsupported isolation fails closed. In-process scripted workflows are rejected outside maintenance because a JavaScript VM in the same process is not an operating-system sandbox.

The mount boundary also makes harness ancestors read-only, preventing ancestor renames. Existing sibling project directories remain writable, but guarded commands cannot create a new entry directly inside an ancestor such as the home directory. Create project directories before launching an ordinary session. Disappearing sibling temporary directories are optional mounts and cannot invalidate the protected mount. A hardlink inventory across the protected roots runs before each guarded command; its overhead varies with filesystem size, mount layout and cache state.

Linux user namespaces can display host root-owned files as `nobody`. OpenSSH rejects included system configuration with that apparent ownership. The launcher projects bounded, byte-identical, read-only copies of trusted `/etc/ssh/ssh_config` and its standard `ssh_config.d/*.conf` targets into the namespace. Only root-owned files under trusted ancestors without group/world write permissions qualify. It changes no host ownership or SSH settings and does not bypass host-key checks. Nonstandard include locations are not automatically projected.

This is a boundary around covered agent mutation paths, not a sandbox for arbitrary third-party extensions or a hostile host user. Pi itself must still write session state. Extensions loaded into its process are trusted code; installing an extension, core patch or external broker grants it host-level capability. A separate process running as the same user, an existing browser/IPC broker, privileged services and external executables reached through such brokers are outside this boundary. Do not run Pi as root. Review additions that expose execution, file writes, subprocesses or IPC before enabling them.

The trusted `render_see` extension starts only its fixed capture program with structured arguments, a private temporary profile, bounded time/output, and Chromium's sandbox enabled. It cannot execute a model-supplied shell command or use a logged-in browser profile. Browser capture runs outside the generic command mount wrapper because nesting Chromium's sandbox inside that wrapper can prevent browser startup. Generic shell/background execution keeps the mount guard. Local asset restrictions, blocked downloads and write requests, and the renderer's browser limits remain in effect.

Hardlinks can alias the same inode through a different path. Native writes compare multiply linked files with protected inode identities; unrelated project hardlinks do not trigger a harness violation. Guarded commands reject hard-linked files with aliases outside the union of protected roots. Multiple links entirely inside those roots remain safe and are allowed. From a maintenance session, run `python3 ~/.pi/agent/scripts/repair-harness-hardlinks.py --help`; review its dry run before applying independent-copy repair. This is a local maintenance operation, never part of public export. Concurrent changes by other host processes are outside the guard's threat model.

Public export is separate from mutation protection. Use the sanitized exporter, review the generated diff, and run the public scanner before publishing. Hooks and CI provide defense in depth; no pattern scanner can identify every confidential sentence. Never publish private backup archives or session histories.


## Shared skill sources

Maintenance protection also covers global skill sources: the active `agent/skills`, `~/.agents/skills`, `~/.codex/skills`, and explicit `skills` paths from the harness's global `agent/settings.json` (for example `~/skills`). The guard captures these paths at trusted module startup. Existing skill symlink entries, their parent links, and their physical referents are included; configured destinations remain protected even before they exist. Changing cwd, clearing environment variables, or launching inside a shared skill directory grants no maintenance authority. Project settings and ordinary project-local `.agents/skills` and `.pi/skills` do not enlarge this global scope.

Native writes, bulk apply and snapshot restore check this same path set. Executable descendants inherit one read-only mount policy for the union of roots, so adding a writable sibling mount for one root cannot expose another. Existing sibling workspaces remain writable. Protecting an absent destination or symlink entry also makes its existing ancestor directories read-only; new sibling entries directly in those ancestors may need to be created before launching the project session, as with the harness root itself.

Unreadable, invalid, excessively broad or unbounded global skill configuration refuses unguarded mutations with a maintenance diagnostic. Global skill configuration for this boundary uses explicit directory or file paths; negative overrides are ignored and glob patterns require replacing them with explicit roots. The active harness remains the sole source of launch authority; shared skill stores never become maintenance launch directories. Configuration and outside-host changes after startup are outside the captured policy; start a new session after changing global skill sources.

# Destructive-operation checks

The filesystem hook assesses foreground `bash` and `bg_run` commands by command role and mutation operands. Copy sources, read-only inventories, quoted prose, heredoc data, and comments do not become deletion targets. Normal cleanup of a specific project or temporary subtree is allowed whether paths are relative, absolute, quoted, or derived from a recognized `mktemp` invocation. Assignments are evaluated in order; later assignments cannot authorize earlier operations. Actual environment values are used, including `TMPDIR`, `TMP`, and `TEMP`; their names alone grant no scope.

Definite system/home/temp-root mutations are blocked even from a broadly rooted session. A whole-workspace wipe or a destructive Git/rsync operation can be reviewed interactively for that exact invocation. Dry runs remain available, and `--force-with-lease` is distinguished from an unconditional force push. No review grants general deletion authority or overrides a hard protected-path decision. Unresolved destructive targets require explicit paths or a simpler command; an unknown value is never silently treated as a temporary directory. Headless runs cannot manufacture interactive approval.

This is bounded accident prevention, not a full shell interpreter or general operating-system sandbox. Complex expansion, sourced scripts, arbitrary Python/JavaScript programs, remote commands and other execution tools are not comprehensively modeled by this hook. The independent harness mount boundary still applies to guarded executable descendants. Concurrent changes by other host processes remain outside its guarantees.

`bulk_edit` applies only a preview issued in the current tool session, bound to the canonical workspace, contents, file identities and modes. Tokens expire after 15 minutes and are consumed on apply. All entries are checked before writing, then checked again at each write; parent symlink escapes are rejected. Writes use exclusive temporary files and per-file atomic replacement. A batch is not an all-or-nothing transaction: cancellation or later I/O failure can leave earlier files changed, and the error reports that count. Use Git or a snapshot for rollback.

Native whole-file writes that would remove over 95% of an existing 16 KiB–2 MB text file require review or an exact-old-text edit. Repetition checks only interrupt large outputs (at least 8 KiB) dominated by one substantive line; ordinary repeated rows and short examples pass. These are contextual error signals, not proof that an edit is incorrect.

## Disposable experiments

`sandbox_run` executes supplied code through its dedicated trusted launcher and a separate Bubblewrap namespace with no writable host mounts, no network and no host credentials. A systemd user service bounds the whole process tree, and the launcher verifies actual cgroup v2 limits before running code. Explicit source inputs are copied through no-follow directory descriptors; symlinks, hard links, directories, special files and oversized inputs are refused. The tool does not grant host shell or project-write access to review agents. See [sandbox lifecycle, limits and threat boundary](SANDBOXES.md).

## Host and device continuity

`sys_probe({action:"host"})` reports bounded OS resources, inherited session indicators, network-interface state/default-route candidates, power status and toolchain presence. `action:"devices"` lists serial, GPIO, I2C, SPI and GPU character-device candidates using metadata only. It never opens a serial port, sends I/O, flashes firmware or starts a stress test. Missing metadata stays unknown; device permissions do not prove identity or authorize a write. Network addresses, gateways, serial numbers and environment values are omitted.

The existing filesystem guard preflights both `bash` and `bg_run`. Recognized connectivity changes, critical service disruption, power/sleep operations, broad process kills, signals to the harness or its ancestors, raw-device destruction and host stress commands are blocked. Diagnostics remain available. Firmware writes and elevated script/test entrypoints require review of the exact invocation. Use compile-only firmware checks, explicit unrelated PIDs or the existing managed-job controls, and bounded `sandbox_run` fixtures where appropriate. An in-session confirmation does not make loss of the active control path safe.

This is bounded accident prevention, not a universal command sandbox: arbitrary programs, script bodies, aliases, remote commands and unsupported shell syntax can have effects outside the visible command. Inspect unfamiliar test/build entrypoints and their privileges before running them. Preserve the actual network, power, mounted-data and control-session dependencies; prepare an independently usable recovery path before operator-led disruptive work. Kernel isolation and resource limits remain separate controls.
