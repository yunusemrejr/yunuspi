# Session observer

The session observer is an independent, conversational quality reviewer. It asks useful questions and offers brief reminders about the main agent's progress, assumptions, user requirements, todo updates, child-agent follow-up, and harness choices. It cannot execute tools, write code, delegate, authorize actions, or change the user's task. Guardians remain narrow local checks.

The observer respects a book: [the Observer Book](OBSERVER-BOOK.md) is 58 chapters of doctrine (engineering, design, color and typography, web, media, operations, science, marketing, communication and more) with the reasoning behind each principle, selected for the current session by deterministic triggers, plus margin notes the observer keeps for each project. It grounds its notes in the passages that apply, can ask to read a chapter before advising, and cites what it used.

During active work, review opportunities start every 30 seconds. Consecutive reviews are separated by at least 30 seconds; each request has a three-minute allowance for provider queueing and reasoning. After a review that adds nothing new (an empty or repeated note with no unread events left), the next review waits 60 seconds, then 120, then at most 240, until something salient happens: a tool error, a test or build result, a plan change, a completion claim, a peer message or a newly fired book trigger. Two consecutive unusable responses (timeouts, truncation, invalid JSON) back off the same way; a first failure still retries at the normal cadence. This inference allowance is independent of the visible check-in cadence: while a review is still running, the TUI shows its model, elapsed time and allowed time within 120 seconds. The main agent keeps working. New advice is shown as soon as it passes validation and current-evidence checks. Check-ins do not pad the main agent's context with repeated suggestions. These timing bounds assume the process/event loop is running; provider availability and fresh evidence cannot be guaranteed by a timer.

The default route is `deepseek/deepseek-flash` through the official DeepSeek API, with high thinking. Change the **Session Observer** role through `/models`, which edits the existing `llm_preferences.json` document. The observer does not change the main session's selected model. For example:

```json
"session_observer": {
  "models": [
    { "provider": "deepseek", "model": "deepseek-flash", "thinking": "high" }
  ]
}
```

When several routes are configured, a route that fails twice in a row cools down for ten minutes while the next configured route serves, with a visible notice. Each review counts once: a timed-out request, which reports at its deadline and again when its cancelled transport settles, is one failure. User restrictions (fixed route, same model, free-only) still apply to the fallback.

Set `"session_observer": { "models": [] }` to disable it. A missing role uses the default; an invalid explicit role is reported as unavailable instead of silently borrowing another model. Existing aliases, reasoning settings and provider restrictions are preserved.

## What the observer sees and how it looks closer

Every review packet carries what the user wants across the whole session: the current request, each earlier user prompt of the session (excerpted, newest six), the harness interpretation of the latest prompt (labelled as a helper's reading, never the user's words) and the user's active `/reminder` texts as standing instructions. Reminder deliveries, Guardian interventions, hook firings and harness guidance sent to the agent appear as labelled events beside tool results, assistant text and provider-returned thinking.

The packet shows excerpts. An in-memory session journal keeps the full text behind every row (prompts up to 128 KiB each, other entries up to 64 KiB, about 3 MB in total with user intent evicted last). During a review the observer can investigate with bounded read-only tools: `session_detail` (full text of any row id, with offsets), `session_search` (all prompts, reminders, thinking and tool output of the session), `read_file` (project files inside the working directory; secret-like paths refused; at most 400 lines), `grep_files` (ripgrep, 40 lines) and `book_read`. At most three rounds of four calls run per review, each result is capped at 6,000 characters, and usage is summed into the review's single receipt. Nothing it can call writes, executes, delegates or reaches the network. `PI_OBSERVER_TOOLS=off` returns to the packet-only review. The TUI note names what the observer looked at.

The instructions ask for one note that matters most: reconstruct the user's intent from every prompt and reminder, compare claims with evidence (looking closer when an excerpt decides the note), spot waste and the wrong tool or skill for the phase, and judge quality as a demanding expert, including originality for visual and open-ended work. Silence is preferred to noise.

A response that cites an unknown evidence id, tool, skill or book passage keeps its paid note: unknown identifiers are removed (and never shown to the agent), an uncited note is delivered as "Uncited observation (verify before acting)", and an over-long note is shortened at a sentence boundary. Control characters, incomplete JSON and copied prompt or thinking text are still rejected. When a review is truncated or times out, the next review uses one lower thinking level (never above the configured level); three clean reviews restore it. Packets are bounded at 10,000 bytes plus the book, and reasoning and answer share an 8,192-token allowance (4,096 truncated high-thinking routes in live sessions).

## Evidence and harness knowledge

Events are read as chronological chunks with a cursor. A successfully validated, current review advances only the events actually included in its packet; an invalid response or advice rejected after a cited state changes leaves the chunk available for the next review. The in-memory queue retains 256 events. Overflow produces a visible coverage notice and explicit incomplete-coverage evidence instead of pretending old work never happened. The original user request remains authoritative in the main session; the observer's excerpt focuses on the actual task after complete mindset wrappers, and marks omitted portions of long requests.

Explicit peer messages sent or received by this exact session are included as untrusted coordination evidence. They do not become user instructions, authorization or model restrictions, and messages owned by another session are rejected.

Each review also receives a deterministic session profile (phase, calls, reads, edits, errors, edited file types, verification runs and whether edits postdate them, rendered checks, open todos, child failures, completion claims), described to the observer as a measurement, not a verdict. It also receives bounded current todo and child-agent status, recently completed tool calls with paths/actions, active foreground commands with elapsed time and timeout, exposed assistant activity, and recent advice. In-progress todos and unresolved child outcomes take priority in these bounded summaries; child execution and acceptance failures include a compact reason when recorded. Provider-returned reasoning is included only when explicitly available. Hidden reasoning is unavailable. No private session archive scan or skill-body read is required.

A source-backed harness map explains direct subagents, scope councils, parallel swarms, provenance-preserving fusion, quality review, todo completion evidence and background jobs. Relevant tools and installed invocable skills are ranked from their metadata for each chunk. Tools are explicitly marked **active** or **discoverable**; a discoverable tool must be activated/discovered before use. Catalog presence does not prove that a feature is enabled or has run. Recommendations must match exact listed names.

Suggestions depend on current work. For example, a long foreground check can be a candidate for background execution when useful independent work remains. A 120-second timeout alone is not evidence of a bad choice, and final verification on the critical path may appropriately stay foreground. The observer does not stop or move an already running command. A separate complete JSON evidence record supplies configured subagent/council/quality-review preferences and relevant explicitly configured swarm/fusion roles, proven-free candidates allowed by current restrictions, observed child outcomes and reported/estimated/unknown costs. Model suggestions must respect these preferences and constraints, use measured usage/performance where present, and acknowledge unknown quality or cost. Execution counts are not quality scores, and unused preferences are not a quota to spend.

The model-routing evidence record (the largest single row) is sent on the first review of each task, when child state changes, when the work concerns models, delegation or cost, or when the observer asks to read `routing`; otherwise a one-line placeholder states that it is unchanged. Chapters of the selected book passages name the tools and skills their doctrine relies on, and those lead the capability shortlist so advice can name them exactly; discoverable tools are delivered with the exact `tool_search` call that activates them.

Packets, including instructions and capability metadata, are capped at 10,000 UTF-8 bytes; the book adds its own separately bounded section (3,400 bytes) between the instructions and the evidence, so static text forms a cacheable prompt prefix. The builder reduces catalog breadth and summaries first, preserves compact current running/completed/todo/child state and the latest advice, and keeps the next unread event. When necessary it reduces model evidence by whole JSON rows with an explicit sampling notice; unknown cost and user restrictions remain intact. This is a bounded evidence sample, not a claim to have read every byte of the session.

## Delivery and freshness

An accepted note appears in the TUI and is prepared for the main agent's next normal model request. It is limited to 150 words and 1,200 characters. The returned-note receipt carries the validated note and exact evidence/tool/skill references. A `prepared-context` receipt records insertion into model context, while `provider-received` requires the native SDK to find the entire ID-tagged capsule unchanged in the final outgoing payload and receive a successful HTTP response for that active session/request. Only the opaque ID, status, time and model route are persisted in delivery receipts. Neither receipt proves the agent understood or acted on the advice.

Preparing context does not consume advice: a pre-dispatch failure or failed request can retry the same fresh note without another timeline message or preparation receipt. After confirmed delivery, later requests remove it. Transport paths without the response callback, including unsupported WebSocket telemetry, leave delivery unknown; a still-fresh note remains eligible for a later request until its normal expiry or invalidation. Older sessions without delivery receipts also remain unknown. Exact and near-duplicate suggestions are suppressed, including across user steering in the same session. Prior advice is included in subsequent reviewer packets to discourage repetition before validation.

Accepted user input, session replacement and model changes always invalidate old observations. Freshness is checked against the evidence actually cited. A note is rejected only when its premise is gone: every cited running command has finished, or routing advice weighed child state that has since changed. Todo, child and completed-tool rows change on almost every step of active work, so a change there does not discard a paid review; neither does later work that overlaps the note's resources, topics or suggested tools, nor older events leaving the bounded queue. Such notes are delivered with an explicit caveat naming the changed state or overlap and asking the agent to check whether it was already addressed. A completed tool call replaces its unread start event, so the queue carries one row per finished call. Notes include their reviewed snapshot identifiers and require checking newer work. Resource/topic matching is a heuristic, not a semantic proof. Unconsumed advice expires after 120 seconds and its freshness is re-checked at delivery. Context advice remains optional and cannot act as a user request or permission.

The observer never wakes an idle agent, interrupts a tool or starts a new user turn. It can show advice while a foreground command runs, but the main agent can consume that advice only at its next model/context boundary. Idle sessions and explicit opt-outs do not generate periodic inference. Reviews start after the main agent's first response of a task; harness preparation before it (prompt analysis, a scope council) is not agent work to judge. Harness-owned automatic runs (scope councils, skill discovery, automatic review) appear as one separate `harness-runs` row and are not counted as the agent's children. A note whose recommended tools and skills were all named by the last three delivered notes, in overlapping words, is suppressed as a repeat.

## Failure, isolation and cost

There is at most one pending observer dispatch. The three-minute deadline requests cancellation and settles the coordinator even if dispatch ignores it. An unsettled dispatch retains its slot, the TUI reports that cancellation was not acknowledged, and no second dispatch is launched. Evidence remains available for the next review after settlement. New user input, session replacement and shutdown still cancel immediately; old results cannot reach the replacement task. A settled SDK wrapper or timeout does not prove that a remote provider stopped computing or billing.

Complete JSON replies may use one Markdown JSON fence, a sentence around the object, line breaks in the note, omitted empty lists, or extra metadata that is discarded. Evidence references and tool/skill names are checked against the packet and the journal ids fetched during the review; registered tools advertised in its harness map remain eligible even when absent from the relevance shortlist. Unknown references are removed rather than voiding the review; incomplete JSON, a final answer that still calls tools and copied protected text are rejected with a specific safe reason. No response body or provider thinking is included in the failure message. The next eligible review can retry unconsumed evidence; there is no hidden retry cascade. Configured-route failure, offline/user restrictions, missing credentials and insufficient output capacity remain explicit constraints. Routes require at least 12,288 context tokens and 4,096 output tokens. Reasoning and answer share a maximum 8,192-token output allowance; native checks may reduce it further.

Session-manager identity and generation own callbacks, evidence and usage. A replaced session cannot receive another session's late advice or billing. Child sessions cannot register an observer. Usage records contain only reported token/cost fields; missing usage is unknown, not free. The observer is counted as auxiliary model work rather than a spawned child agent. Late usage that cannot safely be attached to its original owner remains unknown there instead of being charged to a replacement session.
